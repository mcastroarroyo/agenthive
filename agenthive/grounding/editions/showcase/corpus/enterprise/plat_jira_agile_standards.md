# Jira Taxonomy and Agile Delivery Standards

**Owner:** Priya Raman, Head of PMO (Transformation Office) · **Last reviewed:** 2026-06-20 · **Status:** current

## Purpose

One taxonomy for every programme in the company so that backlogs are comparable, reports roll up across the
portfolio, and backlogs generated by Xenophon (the Pantheon agile analyst) land in Jira without manual clean-up.

## Project keys

- One Jira project per programme. The key has 2–10 uppercase letters or digits and is derived from the programme's
  short name (for example `OTC` for a programme called Order to Cash).
- The Transformation Office's own work uses the project `TXO`.

## Issue types

| Type | Use it for | Sized? |
|---|---|---|
| Epic | A business outcome delivered in 1–3 sprints | No (sum of stories) |
| Story | A user-visible capability that fits in one sprint | Yes, story points |
| Task | Technical work with no direct user value (environments, CI, access requests) | Optional |
| Bug | A defect against accepted behaviour | No |
| Spike | Time-boxed research, maximum 3 days | No |
| Risk | A delivery risk mirrored from the register (Delivery Risk Management Standard) | No |

## Epic naming

`<Workstream code> · <Outcome in plain language>` — the outcome, not the activity.

- Good: "WS · Mailboxes migrated with zero data loss", "AI · Adjusters get a claim summary in under 30 seconds".
- Bad: "Email migration", "Build chatbot".

Workstream codes: **WS** (Workspace), **ID** (identity and security), **DA** (data and analytics), **AI** (agents and
AI), **APP** (application modernisation), **INF** (infrastructure and networking), **CHG** (change management and
training), **PMO** (governance).

## Story format

"As a `role`, I want `capability`, so that `benefit`." Acceptance criteria are written in Gherkin with 1–3
scenarios (Given / When / Then). A story that cannot be written this way is probably a task.

## Labels (mandatory)

- `transformation` on every issue the Transformation Office creates.
- `pantheon` when the issue was generated or refined by the Pantheon agents.
- MoSCoW priority as a lowercase label: `must`, `should`, `could` or `wont`.
- Optional, from a closed list: `business-dependency`, `blocked-external`, `security-review`, `tech-debt`.

Do not invent labels. Request new ones from the PMO so reports stay clean.

## Components

Components mirror the workstream codes above. Every story has exactly one component.

## Priority versus MoSCoW

Jira's priority field (Highest to Lowest) is reserved for bugs. Stories use the MoSCoW label:

- **Must** — without it the release has no value or is not compliant.
- **Should** — important, but a workaround exists.
- **Could** — nice to have; first to drop when time is short.
- **Won't** — explicitly out of scope for this release; recording it keeps the scope conversation honest.

Rule: Must stories may not exceed **60%** of the release's planned points. Above that there is no contingency.

## Estimation

- Fibonacci story points: 1, 2, 3, 5, 8, 13. A 13 means "split it before the sprint".
- Reference-class sizing: compare each story with the Transformation Office's reference stories. Xenophon does this
  with the `estimate_story_points` tool — never guess points.
- Planning velocity before the first sprint: **34 points per two-week sprint** for a standard team of five. Replace
  it with measured velocity after sprint 2.

## Cadence

Two-week sprints. Planning on Monday; review and retrospective on the second Friday (Thursday if Friday is a public
holiday). Backlog refinement once a week for 60 minutes with the business product owner.

## Definition of Ready

A story is ready when it has the story format, acceptance criteria, an estimate, a component, a MoSCoW label, and no
unresolved dependency — or the `business-dependency` label with a named owner and a date.

## Definition of Done

1. Acceptance criteria demonstrated to the product owner.
2. Code reviewed by a second engineer; infrastructure defined as code where applicable.
3. Automated tests pass in CI; for agents, the offline tests pass and the evaluation set does not regress.
4. Security checklist completed for anything touching identity, personal data or external integrations.
5. Documentation updated (runbook, README or knowledge-base document) and owned.
6. Deployed to the test environment with no open S1 or S2 bugs on the story.
7. Moved to Done by the product owner, not by the engineer.

## Workflow

To Do → In Progress → In Review → Ready for Test → Done. "Blocked" is a flag with a reason, not a status. Items
flagged blocked for more than five business days are escalated in the weekly status report.

## Reporting

Weekly: burn-up per release, velocity trend, percentage of Must stories done, blocked items by age, and new risks
raised. The same figures feed the steering committee pack and the quality gate reviews.
